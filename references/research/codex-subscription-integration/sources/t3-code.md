## Bottom line

T3 Code is a GUI/orchestration layer around an externally installed Codex CLI. Its main Codex session integration is **`codex app-server` over stdio JSON-RPC**, implemented through T3’s private local package `effect-codex-app-server`. It does **not** import the official OpenAI TypeScript/Python SDK and does not bundle the Codex binary. It also launches **`codex exec`** separately for short structured-output tasks (commit/PR/branch/title generation).

This matches OpenAI’s primary [App Server documentation](https://developers.openai.com/codex/app-server), which describes app-server as the rich-client interface for authentication, history, approvals, and streamed events.

## Login, subscription, and account reuse

- T3 does not implement an OpenAI login flow or broker subscription credentials. It relies on Codex CLI’s existing local login: `codex login`; provider status is obtained from app-server `account/read`, including ChatGPT plan/email labels. [`providers-codex.md` lines 13–29](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/docs/user/providers-codex.md#L13-L29); [`CodexProvider.ts` lines 70–107](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Layers/CodexProvider.ts#L70-L107).
- OpenAI’s [auth guide](https://developers.openai.com/codex/auth) documents “Sign in with ChatGPT for subscription access”, local credential storage under `~/.codex/auth.json`/OS credential store, and automatic token refresh during use. T3’s source contains no separate subscription-token implementation; **inference:** refresh/reuse is delegated to the Codex CLI/app-server process.
- `CODEX_HOME` is passed to each spawned Codex process. T3 supports a “shadow home” overlay: shared session/config directories are symlinked from the real home while `auth.json` stays a real private file in the shadow home. Thus two accounts can share history/continuation while retaining separate logins. [`CodexHomeLayout.ts` lines 19–65, 320–415](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Drivers/CodexHomeLayout.ts#L19-L65); [`providers-codex.md` lines 43–130](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/docs/user/providers-codex.md#L43-L130).
- Per-provider environment variables are merged into the child process environment; `CODEX_HOME` is resolved/expanded before spawn. [`ProviderInstanceEnvironment.ts`](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/ProviderInstanceEnvironment.ts); [`CodexSessionRuntime.ts` lines 1134–1147](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1134-L1147).

## Permissions, sandbox, MCP, and lifecycle

- T3 maps its four runtime modes directly to Codex app-server thread settings: `approval-required` → `untrusted` + `read-only` + user reviewer; `auto-accept-edits` → `on-request` + `workspace-write` + user; `auto` → `on-request` + `workspace-write` + `auto_review`; `full-access` → `never` + `danger-full-access`. Turn-level sandbox policies are also sent. [`CodexSessionRuntime.ts` lines 487–559](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L487-L559).
- T3 handles app-server server-initiated approval requests for command execution, file changes, MCP elicitation, and user input, queues them as UI events, and returns the user’s decision over JSON-RPC. [`CodexSessionRuntime.ts` lines 1715–1941](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1715-L1941).
- MCP is optional and secondary to the app-server transport. For agent browser access, T3 issues a per-thread bearer credential and injects its HTTP MCP endpoint into Codex with `-c mcp_servers.t3-code.url=...` and `-c mcp_servers.t3-code.bearer_token_env_var="T3_MCP_BEARER_TOKEN"`; Codex then owns the MCP connection/tool calls. [`CodexAdapter.ts` lines 1676–1710](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Layers/CodexAdapter.ts#L1676-L1710); [`ProviderService.ts` lines 262–284](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Layers/ProviderService.ts#L262-L284).
- Each session owns a child process and Effect scope. Close settles pending approvals/input, marks the session closed, closes the scope (which tears down the child), and shuts queues; a 2-second force-kill fallback is configured. [`CodexSessionRuntime.ts` lines 49–67, 2069–2088](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L49-L67); [`CodexDriver.ts` lines 1–20](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Drivers/CodexDriver.ts#L1-L20).

## Versioning, dependencies, and platforms

- T3 does not pin `@openai/codex` in a package manifest; the CLI is external. The Codex driver records `@openai/codex` as the package name for maintenance and offers install/update via detected npm/bun/pnpm/Homebrew routes, generally using `@latest`. [`CodexDriver.ts` lines 63–69](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/Drivers/CodexDriver.ts#L63-L69); [`providerMaintenance.ts` lines 133–175, 276–328](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/src/provider/providerMaintenance.ts#L133-L175).
- The local protocol schemas *are* pinned: the generator uses OpenAI Codex upstream ref [`678157acaa819d5510adfe359abb5d0392cfe461`](https://github.com/openai/codex/commit/678157acaa819d5510adfe359abb5d0392cfe461), dated `2026-07-19`, and writes that ref into generated files. [`generate.ts` lines 20–24, 613–624, 632–635](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/packages/effect-codex-app-server/scripts/generate.ts#L20-L24).
- T3’s server requires Node `^22.16 || ^23.11 || >=24.10`; the desktop distribution documents Windows (`winget`), macOS (Homebrew), and Arch Linux (AUR). On Windows, the desktop can run a Linux backend under WSL; Codex itself must be installed/authenticated in whichever server environment is running the process. [`docs/user/install.md` lines 5–9, 20–50](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/docs/user/install.md#L5-L50); [`apps/server/package.json` lines 1–51](https://github.com/pingdotgg/t3code/blob/a3a8cbd60539b4af4de8f96c892dbd07a2b6c041/apps/server/package.json#L1-L51).

### Relevant package names

`effect-codex-app-server` (private workspace protocol client); `effect` (its runtime dependency); `@openai/codex` (external CLI package name used only for maintenance/update detection); `@t3tools/contracts` and `@t3tools/shared` (T3 settings/types and CLI/shell helpers). No official `openai` TypeScript/Python SDK dependency is declared for Codex.
